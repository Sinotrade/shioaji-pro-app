## 正式期貨新增阻礙：主動回報識別與改刪單請求

- 使用者操作暴露正式期貨改量 HTTP 400：`Please run update_status first to get trade details.`。原始 New 成功 SSE 已包含 id／seqno／ordno；前端投影有更新這些欄位，但 HTTP 改量／改價／刪單只送 trade_id（另含 quantity／price）。
- 已直接唯讀核對當下執行的 1.7.5 `/openapi.json`：CancelOrderRequest 僅 trade_id；UpdatePriceRequest 為 trade_id、price；UpdateQtyRequest 為 trade_id、quantity，皆未定義 seqno／ordno／完整 Trade 輸入。端點清單也未提供僅合併回報識別的同步入口；不能隨意增加未定義欄位並宣稱已修復。
- 本機 SDK 原始碼版本較舊，僅可作調查線索，不能作 1.7.5 快取實作的確證。最初 place_order HTTP 回應與當時 SDK cache 未保存；確切缺失欄位及競爭順序尚待確認。上游問題已依使用者授權發布為 [Shioaji #235](https://github.com/Sinotrade/Shioaji/issues/235)，見下節。
- 真實期貨 fixture 覆蓋不同 id 的拒絕 New 與成功 New、初始 PendingSubmit 缺識別被 New 回報補齊，以及 Cancel 的 order_quantity 仍為原量 3、cancel_quantity 3 時正確顯示取消。這是投影回歸，不代表原生改量 HTTP 400 已修好。
- 另確認前端 HTTP settled 與 SSE 競爭會留下「結果待確認」提示。第一份自動關聯草案因可能將延遲或外部同類操作誤配而被自動審核拒絕，獨立 review 也不核准；草案未套用，相關未完成支援復原，不以自動確認或自動重送掩蓋不確定結果。此缺陷仍保持待修／待驗。
- 使用者後續以新的期貨 2 口委託執行刪單，同樣收到 HTTP 400 `Please run update_status first to get trade details.`；期貨改量與刪單均列為未通過。先前另一筆 3 口委託收到 Cancel 成功回報，不可拿來替代本筆刪單驗證，也不能概括宣稱期貨刪單已正常。

## 期貨改刪單的暫時相容處理
